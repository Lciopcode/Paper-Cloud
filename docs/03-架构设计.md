# 论文云 · 架构设计

> 目标：**高内聚低耦合**。
> 本文定义模块边界、依赖方向与契约。改动结构前先改本文，再改代码。

---

## 一、分层与依赖方向

```
┌─────────────────────────────────────────────────────────────┐
│ 离线管线（Node）        │ GPU 管线（Python）  │ 前端（浏览器）  │
│ pipeline/               │ pipeline_gpu/       │ src/ui/        │
│                         │                     │ src/three/     │
│  数据抓取与构建          │  embedding/聚类      │  渲染与交互     │
└───────────┬─────────────┴──────────┬──────────┴───────┬───────┘
            │                        │                  │
            ▼                        ▼                  ▼
      ┌───────────────────────────────────────────────────────┐
      │  引擎层 src/engine/  ← 唯一真相来源，纯函数、零依赖      │
      │  spine.ts（编号双射） · tokenize.ts（分词）             │
      └───────────────────────────────────────────────────────┘
                              ▲
      ┌───────────────────────┴───────────────────────────────┐
      │  数据层 src/data/  ← 契约与加载                          │
      │  domains.ts（学科契约） · contract.ts（资产契约）        │
      └───────────────────────────────────────────────────────┘
```

### 依赖规则（**硬约束**，违反即架构腐化）

| 层 | 目录 | 可以依赖 | **禁止**依赖 |
|---|---|---|---|
| 引擎 | `src/engine/` | 仅自身 | 数据层、three、React、DOM、`node:fs` |
| 数据 | `src/data/` | 引擎 | three、React、DOM |
| 状态 | `src/state/` | 引擎、数据 | three 对象、React 组件 |
| 渲染 | `src/three/` | 引擎、数据、状态、three | `node:fs`（必须走数据层） |
| 界面 | `src/ui/` | 状态、数据 | 直接操作 three 对象 |
| 离线路据 | `pipeline/` | 引擎（**同一份文件**）、数据 | three、React |
| GPU 管线 | `pipeline_gpu/` | 无（独立 Python） | 只读 `text/` 与 `rank.bin`，只写 `semantic/` |

### 为什么管线必须 import 同一份引擎

引擎是编号（`index = rank(title)`）的唯一实现。如果离线用一套、浏览器用另一套，
一旦有细微差异，用户点开论文就会"编号对不上"——**这种 bug 不会崩溃，只会给出错误答案**，
比崩溃难查得多。所以：**引擎只有一个实现，双方都 import 它**。

实现方式：`pipeline/*.mjs` 直接 `import { ... } from "../src/engine/spine.ts"`。
Node 24 能原生跑 `.ts`，所以不需要编译步骤，也不需要复制代码。

## 二、引擎层（`src/engine/`）

### 2.1 `spine.ts` —— 编号脊柱

**职责**：标题 ⇄ 编号的精确双射。**不做**：不认识"论文"、不读文件、不管元数据。

| 导出 | 作用 | 不变量 |
|---|---|---|
| `rankSpine` / `unrankSpine` | 词 id 序列 ⇄ 编号（定长 base-V，**首位是最高位**） | `unrank(rank(x)) === x` |
| `prefixIndex` / `prefixSpan` | 半编号：前缀锁定的连续区间与可能数 | 区间内每一号都以该前缀开头 |
| `scatter` / `unscatter` | 双射散射（让相邻编号在空间上不相邻） | 在全目录上是**双射** |
| `indexForTitle` / `titleOfIndex` | 对外接口（分词由调用方注入） | 可编则必可解 |
| `feistelPermute` | 位宽 2h 的平衡 Feistel 置换 | 在整块上可逆 |

**关键设计决策（都在代码注释里写明了原因）**：

1. **首位是最高位**：这样"标题开头相同"的编号落在连续区间，半编号才有意义。
2. **散射用 width-2h + 固定宽度 cycle-walk**，而不是诗云的"半宽 cycle-walk"：
   后者在 R 不是"置换的并集"时**不是双射**（我们实测复现过重复值）。
   宽度必须在循环**外**定死一次——循环内按当前值重算宽度会让逆变换回不去。
3. **8 轮 Feistel**：4 轮的雪崩不足，相邻编号散开后仍有可见条带。

### 2.2 `tokenize.ts` —— 分词

**职责**：标题 → 词序列。**放在引擎层的原因**：编号的唯一性完全依赖分词一致性。

设计取向：**保守**。宁可把相近的词当不同词（编号略有冗余），也不合并不同词（会造成编号冲突）。
因此刻意**不**把 `new`、`case`、`model`、`learning`、`network` 这类有区分度的词当停用词。

## 三、数据层（`src/data/`）

### 3.1 `domains.ts` —— 学科契约（八层里的第①层）

`DomainSpec` 含 id、中英名、arXiv 分类前缀、颜色、宇宙坐标、半径、朝向、一句话说明。

**为什么分类写死在这里**：学科划分是**策展结果**（人类决策），不是统计结果。
arXiv 的 `primary_cat` 只是"投稿时选的分类"，有大量跨领域与误选。
把它归并成 8 个学科是本作品的设计决策，必须显式、可审计、可修改。

**归团原则**：按 `primary_cat` 归团（一篇论文只进一个星系），
避免同一篇论文出现在两处让"论文之间的关系"变含糊。

### 3.2 `contract.ts` —— 资产契约（**待写**）

定义管线产出、前端消费的全部数据结构。原则：**契约先行**——改结构先改这里与文档。

计划包含的契约（对应 `docs/01-规划与指导.md` 的八层）：

| 契约 | 内容 |
|---|---|
| `Manifest` | 总清单：学科列表、各团篇数、层级统计、版本 |
| `CatalogAsset` | 词表 + 词槽数（引擎输入） |
| `SpineAsset` | 标题编号脊柱（每篇的编号、词 id 序列） |
| `HierarchyAsset` | 八层层级的节点树（id、名称、父节点、篇数、质心） |
| `PaperAsset` | 单篇元数据（标题、作者、摘要、分类、年份、引用、venue 等级） |
| `RelationAsset` | 三类边（引用/同领域/同路线）+ 反向索引 |
| `RouteAsset` | 技术路线（恒星）：id、标签、质心、规模、代表论文 |
| `EmbeddingAsset` | 256 维 int8 向量（GPU 产物） |

> **落地情况（2026-10 更新）**：契约已经写在 `src/data/contract.ts` 里，
> 但**实际字段与上表不完全一样** —— 以代码为准。已实现的是：
> `Manifest` / `DomainEntry`（含 `strata`、`relations`、`cites`、**`semantic`**）、
> `SpineRecord` / `PaperPoints`。
> GPU 语义层那一族统一收在 **`SemanticAssets`** 一个接口下（emb / clu / route / labels / communities），
> 消费端在 **`src/data/semantic.ts`**（照 `cites.ts` 的先例独立成模块，
> 而不是塞进通用资产层 `assets.ts` —— 那里放的是脊柱/编号表/元数据这类"所有学科都一样"的资产）。
> 上表里的 `CatalogAsset` / `HierarchyAsset` / `RouteAsset` 是早期规划名，
> 分别对应代码里的 `VocabAsset`、`DomainEntry.strata` + `src/data/hierarchy.ts`、
> 以及 `SemanticAssets.communities` + `SemanticAssets.labels`。

## 四、渲染层（`src/three/`）

### 4.1 八层层级 ↔ 宇宙元素的坐标求解

| 层 | 宇宙元素 | 位置由什么决定 | 视觉预算 |
|---|---|---|---|
| ① 学科门类 | 宇宙网 | 契约里写死（策展） | 8 个节点 |
| ② 一级学科 | 超星系团 | 父节点内的角向哈希 + 半径 ∝ √count | 每团 3–8 个 |
| ③ 大研究方向 | 星系群 | 同上 | 每团 5–30 个 |
| ④ 子研究方向 | 星系 | 同上（**星系本体**：旋臂盘在这里出现） | 数十个 |
| ⑤ 课题方向 | 星团 | 同上 | 数百个 |
| ⑥ 具体研究点 | 星云 | 语义聚类质心 | 数千个 |
| ⑦ 技术路线 | 恒星 | 社区中心 | 视视野而定 |
| ⑧ 论文 | 行星 / 小行星带 | **规范位置**（见 §4.3） | ≤30 万点 |

**渲染预算硬约束**：任何时刻屏幕上的点不超过 30 万。
手段：分级 LOD（只画当前层 + 直接子层）、视锥裁剪、渐进流式加载。

### 4.2 三类关系边（对应"论文与论文的关系"）

| 边 | 学术含义 | 数据来源 | 方向 | 视觉 |
|---|---|---|---|---|
| **引用** | 应用 / 被应用 | Semantic Scholar `/references` | 有向 | 弧线，亮度随年份/强度 |
| **同领域** | 同一领域 | OpenAlex 层级（domain/field/subfield/topic） | 无向 | 淡色带 |
| **同路线** | 同一方向上的同一路线 | 语义近邻 ∩ 共被引/文献耦合 → 社区发现 | 无向 | 星尘流 / 拉格朗日点 |

**为什么"同路线"要两路证据交叉**：只靠语义近邻会把"用了同一套方法的不同领域论文"误判为同一路线；
只靠引用又会漏掉"尚未互相引用但确实同源"的新论文。两路都指向时才成立。

### 4.3 坐标稳定性（双坐标）

三种排列模式（时间顺序 / 影响力 / 综合）会重排位置。若不处理，用户"记不住东西在哪"，永久链接也会失效。

| 坐标 | 定义 | 用途 |
|---|---|---|
| **规范位置** canonical | 层级 + 引用拓扑决定，**永不变** | 永久链接指向它；跨会话稳定；默认视图 |
| **模式视图** mode view | 在规范位置上按权重做一次布局变换 | 切模式时平滑过渡，切回即复原 |

### 4.4 拾取与亮度解耦（关键）

**亮度与可拾取性必须解耦**，否则"把星系调亮"就会让拾取失效。方案：GPU 颜色 ID 拾取 ——
离屏渲染时每个点用自己的 id 作颜色，点击时读回像素即可反查是哪个点，
与屏幕上显示的亮度完全无关。这是敢用 bloom 把星系做亮的前提。

## 五、状态层（`src/state/`）

单一 zustand store，但**按域切片**（每个 slice 一个文件），避免一个巨型文件：

| slice | 内容 |
|---|---|
| `data` | manifest、各学科运行时、加载状态 |
| `view` | 相机、当前层级、可见范围、LOD |
| `select` | 选中的论文 / 星团 / 路线 |
| `search` | 检索模式、查询、结果、**命中集合**（用于星空过滤） |
| `rel` | 关系图显隐、局部图、边过滤器（Obsidian 式） |
| `mode` | 三种排列模式 + 双坐标过渡状态 |

跨域重置纪律：换选中目标时必须清理派生状态（否则会串台）。

## 六、GPU 管线（`pipeline_gpu/`）

**完全独立**：只读 `text/*.jsonl.gz` 与 `public/data/<domain>/rank.bin`，
中间产物写在仓库根的 `semantic/`（**不是** `emb/`、`cluster/` —— 那是早期规划用的名字），
最终由 `export.py` 转成前端能读的 `public/data/semantic/`。前端**不**依赖 GPU 算力。

| 步骤 | 输入 | 输出 |
|---|---|---|
| `embed.py` | `text/*.jsonl.gz` | `semantic/<d>/emb-<start>.i8`（`LUNYEMBS` 头 + 256 维 int8），每 20 万篇一片、可续跑 |
| `cluster.py` | 上一步的分片 + `rank.bin` | `semantic/<d>/clu.bin`（**层内**自适应聚类，第 5 层） |
| `knn.py` | 分片 + `rank.bin` | `semantic/<d>/knn-k20.bin`（**层内** k-NN，k=20；faiss GPU 优先，无 GPU 自动退回 CPU 精确检索） |
| `community.py` | k-NN 图 | `semantic/<d>/route.bin`（同路线边）+ `communities.json`（Leiden 社区 = 第 6 层） |
| `label.py` | `clu.bin` + 标题 | `semantic/<d>/labels.json`（c-TF-IDF 关键词给每个研究点起名） |
| `export.py` | 以上全部 | `public/data/semantic/<d>.{emb,clu,route,cmu}.bin` + `.labels.json` + `.communities.json` |
| `register.py` | 上一步产物 | 登记进 `public/data/manifest.json` 的 `domains[*].semantic` |

**几个与早期规划不同的取舍**（都以代码注释为准）：

- **不是"簇内建边"而是"层内建边"** —— 层是构建期写进编号的 L3 研究方向；
  簇（第 5 层）是层内再聚出来的，粒度更细，用它建边会让跨簇的同路线论文连不起来。
- **`k` 不是多分辨率的一组固定值**，而是每层自适应 `clip(round(sqrt(m/2)), 2, 64)`；
  不足 4 篇的层跳过聚类（簇号恒为 0，表示"这一层只有一个研究点"）。
- **相似度阈值 0.65**（原来拍的是 0.80，实测会把图切碎，见 `community.py` 顶部那张表）。
- **`.ok` 是产出指纹**，不只是"跑过了"：换过模型/维度/序列长度/分片大小都会重算，
  避免"两个模型的向量混在一起而验收还全绿"。

**断点续跑是硬要求**：GPU 任务可能被打断（全量约 5.8 小时），
分片即持久化单位即进度单位，重跑同一命令即可接着来。

> 实现细节与格式契约见 `pipeline_gpu/README.md`；
> 前端消费端见 `src/data/semantic.ts` 与 `src/data/contract.ts` 的 `SemanticAssets`。

## 七、部署形态

| 形态 | 说明 |
|---|---|
| **纯静态** | 无后端、无账号、不收集任何用户数据（合规优势，也是"数据安全意识"的加分点） |
| 首屏预算 | **≤ 2 MB**；其余全部按需流式加载 |
| 资产压缩 | brotli 预压缩，由静态服务器带 `Content-Encoding: br` 提供 |
| 离线包 | 除在线网址外，另出一份可离线运行的包（评委网络不可控） |

## 八、放在别处的依赖（要记住的耦合点）

| 依赖 | 位置 | 为什么这样 |
|---|---|---|
| arXiv 语料库 | **本交付里在 `../corpus`**（与仓库同级，5.4 GB） | 可由 pipeline 重建，不值得复制。结构是**每学科一个 SQLite**：`domain_<id>.db`（physics 2.47 GB / cs 1.50 GB / math 0.67 GB…）+ `freq.db` + `report.json`；`pipeline/export-text.mjs --corpus` 可改指。八团篇数、年份区间、词表规模的**权威值**都在 `corpus/report.json`（合计 3,052,327 篇 / 245 分片） |
| 引用计数 | `data/cites/`（`harvest-cites.mjs` 产出）+ `public/data/cites/`（`LUNYCITE` 亮度表） | 第三方限速抓取，**不可再生**，应随交付一起带走。⚠️ **两处都是"一篇一个数"，不是引用边**：`data/cites/<学科>.bin` 每 8 字节一条、**按 docId 索引**，布局是 `u32 cites \| u16 year \| u8 venueTier \| u8 flags`（无文件头）；`public/data/cites/<学科>.bin` 才带 `LUNYCITE`。实测物理团 11,708,704 ÷ 8 = 1,463,588 条 = 论文数。**"谁引用了谁"从来不存在** ⇒ 共被引这一路无从算起，`community.py` 会如实降级（详见 `pipeline_gpu/README.md` §3） |
| 诗云参考原码 | `../shiyun`（只读参考） | 语义层与拾取方案的设计参考；**不参与构建**，无代码依赖 |
