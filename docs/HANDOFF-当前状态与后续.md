## 零、怎么把它跑起来

```bash
cd v2/lunyun
node deploy/serve.mjs --port 5311      # 本地服务器（支持 HTTP Range，见下）
# 浏览器打开 http://127.0.0.1:5311
node deploy/verify.mjs                 # 端到端自检（应当"全部通过"）
```

数据已经构建好并落盘，上述命令**不需要任何网络**（除首次 `pnpm install`）。

**资产不可压缩的例外**（重要，别顺手"优化"掉）：
`public/data/meta/*.{idx,txt,abs,venue}.bin` 与 `public/data/search/*.idx.bin`
**必须保持未压缩**。浏览器用 HTTP `Range` 从里面精确取字节
（实测：从 93,669,664 字节的索引里取 256 字节）。压缩后无法随机访问，
而且**报错会非常难懂**（拿到的是压缩流的一段，看起来像"内容坏了"）。
`deploy/serve.mjs` 里有 `RANGE_EXTS` 显式排除 brotli，构建脚本也不再生成对应的 `.br`。

### 1.8.1 三种排列模式（`src/three/layout.ts`）——全部可用

模式切换**不重算编号** —— 位置仍由地址唯一决定，只是把同一批点按另一套纯函数规则摆一遍。
所以永久链接、层级归属全不受影响（`layout.test.ts` 17 项守的就是这个确定性）。

| 模式 | 摆法 | 现状 |
|---|---|---|
| **领域**（默认） | 8 座独立旋涡星系 | ✅ |
| **时间** | 一片盘状星系，对数螺旋，内圈最老 → 外缘最新（1986–2026） | ✅ |
| **影响** | 引力井：半径 ∝ 被引次数（对数） | ✅ 见 §3.4 |

**时间模式的关键取舍（这是做这一步最有价值的发现）**：
第一版按"年份等宽"排，画出来是个**甜甜圈** —— 论文全挤在外圈、中间一大片空白。
查数据才知道原因：arXiv 论文量随时间**指数增长**（物理团实测 1986 年 1 篇、
1996 年 12,166 篇、2016 年 58,241 篇、2026 年 84,751 篇，**累计到 2016 才过 50%**）。
所以那不是 bug，是真实增长率被等宽映射挤到了边缘。

改成**按论文量等分**（每一篇占同样的半径增量）：盘面密度均匀，而刻度环仍标真实年份，
于是**环的疏密本身就画出增长率** —— 1990 年代的环几乎贴在一起，2020 年代的环拉得很开。
依据是 `manifest.domains[*].meta.yearCounts`（年份直方图，每年一个数）。

### 1.8.2 三种交叉可视化（依据真实统计，不是装饰）

**跨星系星桥**（`Bridges`）：强度来自 `manifest.domains[*].bridges` ——
本团有多少篇论文挂了对方学科的 arXiv 分类。实测图景本身就有信息量：

```
eess → cs       80,572   电子工程的论文大量挂计算机分类
cs   → math     79,529   ┐ 双向都大
math → cs       76,313   ┘ ⇒ 真正融合的两个领域
physics → math 105,316   物理是最大的枢纽
econ → qfin      6,291   ┐ 强烈单向
qfin → econ        565   ┘ 金融工程很少挂经济分类
```

所以桥**有方向**（颜色从起点学科渐变到终点学科），拱起的弧避开星系盘。

**星尘流**（`toggleCrossOnly`）：只留**跨学科论文**亮着 ——
星桥显示的是"两个领域有联系"的**强度**，而星尘流补上另一半：
"联系是由哪些具体工作建立的"。复用检索那套 `aDim` 机制，没有新增着色器代码。
判据来自元数据索引 flags 字节的 bit0（构建期从 `cats.length > 1` 得出）。

实测：可见 61,050 点中 **29,665 颗跨学科，占 48.6%** ——
所以打开后画面变化不 dramatic，因为**大部分 arXiv 论文本来就挂多个分类**。
这是数据事实（自检把这一比例也断言了，落在实测区间才通过）。

| 实测吞吐 | 8–500 篇/秒，**波动极大** | 并发 6 时 370 篇/秒 |
| 日配额 | 匿名共享池，**无硬性日上限** | **1000 次/天**（不是宣称的 10 万次） |
| 全量 305 万篇 | 6,105 次请求 ⇒ 数小时 | 30,524 次 ⇒ **30 天，跑不通** |
| 回映射 | 原样回显 arXiv id（天然可靠） | 需三级回映射，实测 **95.8%** |

OpenAlex 的配额是从**响应头**读出来的：

```
x-ratelimit-limit: 1000          ← 每天 1000 次
x-ratelimit-remaining: 0
retry-after: 46312               ← 用尽后 12.9 小时才重置
```

我按"10 万次/天"估算出 51 分钟，跑了几万次之后被 429 挡住才发现。
**教训：别信文档里的额度，去读响应头。**

三级回映射（OpenAlex 会把 arXiv 的 DOI 合并进期刊版记录，
返回的 `doi` 往往不是查询的那个）：
① 期刊 DOI 精确匹配（语料库 `doi` 列，物理团 104 万条可用）
② arXiv 号（从 `locations[].landing_page_url` 正则找）
③ 归一化标题兜底

**只做 ②③ 时物理团只有 72.9%** —— 也就是说 27% 的论文会被算成 0 引用、
表现为**假性变暗**：不是缺失，是错的方向。加了 ① 之后 **95.8%**。

### 3.3 引用边（第一类关系）—— 被配额卡住

格式已定在 `src/data/relations.ts`（`EDGE_KIND.cites`，有向）。但两条路都走不通：

- **S2 `/references`**：**不能批量**，一篇一次请求。20–30 万篇 × 1 请求/秒 = 80+ 小时。
- **OpenAlex `referenced_works`**：可以批量，但需要先建
  「OpenAlex ID → 我们的 docId」映射表，那又是 30,524 次请求（30 天）。

所以引用边**不是"没做"，而是"在当前配额下做不了"**。
要做得先拿到 API key（S2 提供免费学术 key，需要在官网申请）。

### 3.8 八层视觉下潜 —— 已落地为「研究方向下潜」

规划里的"八层"（宇宙网 → 超星系团 → … → 行星）在本版架构下落地为：
**8 个学科星系（L1）→ 一级学科（L2）→ 研究方向（L3）**，并且**可以真的下潜**：

点层级面板里任一研究方向 → **只留那个方向的论文亮着**（其余压暗），可取消。

为什么这是"下潜"而不是"又一个筛选"：层号在构建期就写进了每篇论文的编号
（编号 = [层号][层内编号] → 标题 → 坐标），所以"只看某一层"是一次 O(1) 判断，
**不需要任何新数据、不需要重新索引**。

实测（`node deploy/verify-drill.mjs`）：点「凝聚态物理·材料科学」后，
物理团 29,272 点里只留 1,440 点亮着（4.9%），其余 7 个星团不受影响。

## 四、已知的边界与诚实说明（写给评委看）

1. **arXiv 是 STEM 预印本库，不是"所有论文"**。说"全部开放论文"时应限定为
   "arXiv 全部开放获取元数据"。
2. **作者名未做消歧**。同一个名字可能对应不同人，本项目不做作者维度分析。
3. **发表评级是可审计的启发式，不是权威排名**。规则在一个文件里，可读可改可反驳；
   认不出返回 T0，不猜。
4. **虚空拉取报告的是"最近的真实论文"**，不是"这个编号上恰好有论文"——
   相邻论文的编号间距约 10⁵⁶，要求精确命中等于没有功能。
5. **演示视图是抽样**（每 50 篇 1 点）。面板里的"相关论文"可能不在当前抽样中，
   此时会跳到**最接近的**那一篇并说明距离，而不是静默失败。

## 五、踩坑记录（这一节最值得读）

这一轮修的问题里，有一类特别值得记：**源码看着正常、构建不报错、测试也通过，
但结果就是错的**。它们比崩溃危险得多，因为没有任何信号提示你去查。

### 5.1 三个"永远通过"的空判据

自检脚本里曾经有三条判据**什么都没验**，而它们一直是绿的：

| 判据 | 为什么是空的 |
|---|---|
| `rankIsBigInt` | 写的是 `typeof (rt.rankTable ? rt.rankTable.minRank : 0n)`。`rt` 是采样**之前**捕获的旧快照，而加载编号表后 store 会 `set()` 出**新对象** —— 旧快照里 `rankTable` 仍是 `null`，表达式退化成 `typeof 0n` ⇒ 恒为 `"bigint"` |
| `minRankDigits/maxRankDigits` | 同上，读到 `0/0`，判据 `0 ≤ 73` 恒真 |
| "标题一致性"交叉核对 | 60 个随机样本的 `resolvable` **全是 false**（演示视图每 50 篇一颗星），于是每条都被静默跳过；唯一触发的一次又因为漏传 `nearDocId`、筛选条件写成 `p.nearDocId !== null`（**`undefined !== null` 为 true**）而选错论文，误报成"不一致" |

**修法与原则**：改用"**必须找到至少一个**"的断言形式，
并把交叉核对改成**确定性**的（从演示点集里均匀取 5 篇，两条链路取标题逐字比对）。
改真之后第一次运行就报出"差 12 篇" —— 那是第四个坑（见下）。

### 5.2 基准量用错：把"上界"当成"真实篇数"

上面那条判据报 `1,463,588 vs 1,463,600`。查下来数据是干净的，是**我的基准错了**：
用的是 `spine.count`，而**演示脊柱的 count 是 `records × stride`，即上界**，
只用于 `get(docId)` 的越界检查（`assets.ts` 里早就写了"真实篇数由调用方从 manifest 取"）。
29,272 × 50 = 1,463,600 正是那个数。

顺带发现我用了个**不存在的属性** `spine.isDemo`（`!!undefined` 恒为 false，
把"演示脊柱"标成了"非演示"—— 又一个空判据）。补了真实字段。

### 5.3 CSS 注释里写"注释结束符"会提前结束注释

桌面（1582px）上冒出了本该只在窄屏显示的抽屉把手。源码、构建、测试全都正常，
**只有浏览器的 CSSOM 里那条规则不见了**。

根因追到两层，而且第二层是我在修第一层时踩的：

1. 我写脚本把整块响应式 CSS 从文件中部搬到末尾，**新拼的说明注释自己带了结束符**，
   而原文正文（开头的注释起始符已被正则去掉）就悬在注释外变成了 CSS 垃圾 ——
   解析器在错误恢复中把紧随其后的 `.hud-handle{display:none}` **一起吞掉了**。
2. 修第 1 条时，我在注释里**引用了那个两字符结束符来说明问题** —— 于是又踩一次。

**教训**：用脚本拼代码块，必须验证**拼接后的文件能被目标解析器正确解析**，
不能只看"文本写进去了"。也为此加了 `deploy/verify-css.mjs`：
直接问浏览器 CSSOM 里有没有那几条关键规则。

### 5.4 在模板字符串里写反引号（踩了四次）

`deploy/*.mjs` 里到处是"把代码当字符串塞进浏览器"的模板字符串；
`src/three/shaders.ts` 里的 GLSL 也是。在这种字符串**内部**写反引号会把它切断，
症状是 `SyntaxError: missing ) after argument list`，而且**报在模板开头那一行**。

更坑的是：一行里写**两个**反引号时奇偶性不变，所以"数反引号个数"的检查会放过它。

四次之后写了 `deploy/lint-embedded.mjs`（逐行状态机，扫 49 个文件），
并且**验证了守卫本身真的会报错** —— 造一个含反引号的模板文件，它报错并 exit 1。

### 5.5 其他

- **manifest 只写 `.json` 不写 `.br`**：`serve.mjs` 对支持 br 的客户端优先发压缩版，
  于是浏览器读到的还是**上一次构建的压缩副本**，表现为"脚本说登记成功了、界面上看不到"。
  五个 build 脚本里只有 `build-cites.mjs` 漏了。
- **分片粒度决定数据安不安全**：抓取器原来 400 批一个分片，进程死在片中间时
  整片一个字节都没落盘，而进度已标完成 —— 重跑**静默跳过 11 万篇**。
  现在"分片 = 持久化单位 = 进度单位"，并在启动时对照实际文件清理假进度。
- **`fetch()` 有 try/catch 但 `res.json()` 没有**：连接中途重置时抛
  `TypeError: terminated`，直接把跑了 10 万篇的任务干掉。
- **别提"按 CPU 占用"杀进程**：我用 `Get-Process node | Where CPU -lt 3 | Stop-Process`
  清理进程，把正在跑的抓取任务误杀了，白停 71 分钟。
- **服务器不需要重启**：`serve.mjs` 每次请求都从磁盘读 `dist`，重建后刷新页面即可。
