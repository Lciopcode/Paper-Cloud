# 04 · 引用数据获取（Semantic Scholar API key 申请与建图）

> 这份文档只解决一件事：**怎样把"谁引用了谁"弄到手。**
> 它是一份操作手册，不是设计文档 —— 每一步都能照着做，每一条结论都有实测数据支撑。

---

## 0 一句话现状

**库里现在没有任何"引用对"。** 画"引用/被引用"关系之前，必须先把它建出来；
建它需要 Semantic Scholar 的 API key（免费申请，一个表单）。

---

## 1 现状：我们手上有什么、缺什么

### 1.1 有的

| 东西 | 位置 | 内容 |
|---|---|---|
| 语料 | `corpus/domain_<d>.db` | 3,052,327 篇 arXiv 论文的题录 |
| 被引**次数** | `data/cites/<d>.bin` → `public/data/cites/<d>.bin` | 每篇 8 字节：`u32 cites \| u16 year \| u8 venueTier \| u8 flags`，**按 docId 索引** |
| 语义近邻 | `public/data/semantic/<d>.route.bin` | 3,326 万条「同技术路线」边（由标题+摘要嵌入算出），`u32 a \| u32 b \| f32 w` |
| kNN 图 | 中间产物 | 各团 20 近邻边（物理团 2,927 万条） |

### 1.2 缺的

**"A 引用了 B"这种一条一条的边，任何文件里都没有。**

`harvest-cites.mjs` 当年调 Semantic Scholar 的 batch 接口时，`fields` 只要了
`citationCount,externalIds,year` —— **只要了计数，没要引用列表**。
这不是 bug，是当时的需求（要把"引用次数 → 星球亮度"接进渲染，不需要边）。

### 1.3 语料里也没有

`corpus/*.db` 的 `papers` 表字段是：

```
id, title, abstract, authors, cats, primary_cat, created, updated,
comments, journal_ref, doi, license, msc, report_no
```

**没有 references / citations 字段。** 上游的 arXiv 题录本身就不含参考文献。

## 2 三个源的实测对比（2026-10 实测，脚本见 `_scratch/probe-*.mjs`）

| 源 | 能拿到引用吗 | 能对回我们自己的库吗 | 结论 |
|---|---|---|---|
| 本地语料 | ✗ 没有引用对 | — | 不可用 |
| OpenAlex | ✓ 每篇 7–69 条 | **✗ 285 条只中 2 条（0.7%）** | **不可用** |
| Semantic Scholar batch | ✓ | ✓ 按 arXiv 号**精确**映射 | **唯一可行，需要 key** |

### 2.1 为什么 OpenAlex 不行（这个坑很容易踩第二次）

OpenAlex 把 arXiv 的**预印本记录合并进了期刊版**记录。于是：

* 我们按 `10.48550/arxiv.<id>` 查得到那篇论文 ✓
* 它给出的 `referenced_works` 也是真的 ✓
* 但批量反查回来的对端，DOI 是**期刊 DOI**（`10.1016/...`、`10.1109/...`），
  而我们的库是**纯 arXiv**，只有 14.6% 的论文有 DOI 字段 —— **口径上就对不上**。

实测：从一个 DOI 反查 50 个 `referenced_works` 只要 368 ms、能拿回 DOI，
但按 DOI 匹配本地只有 **5.8%**，按标题匹配再补一点，合计仍然个位数百分比。
另试了"从 DOI 里抠 arXiv 号"（`10.48550/arXiv.cs/9912021` 这种形态）：
**285 条里只有 3 条带 arXiv DOI** —— 因为 arXiv 预印本记录已经被合并掉了。

> 这个教训写在这里是为了**避免重复投入**：OpenAlex 本身很好用（CORS `*`、10 请求/秒、
> 免 key），但它适合"做外部检索"，不适合"映射回一个纯 arXiv 的本地语料"。

### 2.2 为什么 Semantic Scholar 行

它的 paper 标识支持 `ARXIV:<id>`，返回值里的 `externalIds.ArXiv` 也是 arXiv 号 ——
**两端都是 arXiv 号，映射是精确的，不经过 DOI。**

### 2.3 它现在的障碍：匿名限流

实测（`_scratch/probe-s2-availability.mjs`）：

```
单篇端点 第 1 次: HTTP 429  5153 ms
单篇端点 第 2 次: HTTP 429  5899 ms
batch  端点     : 连接超时
```

匿名配额已经被打到硬限流，而且响应**没有 CORS 头**（浏览器直接调不通）。
必须申请 key，并且抓取只能走本地脚本（Node），不能走浏览器。

## 3 申请步骤

### 3.1 填表

1. 打开 **<https://www.semanticscholar.org/product/api#api-key-form>**
   （`#api-key-form` 这个锚点会直接把页面滚到表单）
2. 表单要填的项与建议填法：

   | 字段 | 建议内容 |
   |---|---|
   | Name / Email | 真实姓名与常用邮箱（key 发到这个邮箱） |
   | Affiliation | 学校 / 单位 / 个人项目都可填 |
   | Intended use | 照实写，例如下面那段 |
   | Expected request volume | `~6,200 requests total, paced at 1 request/second` |

   用途说明可以直接抄这段（英文，照实描述即可）：

   > Academic, non-commercial research visualization. I maintain a local corpus of
   > 3.05M arXiv papers and need to build the citation graph between them, restricted
   > to papers present in that corpus. I will use only the `/paper/batch` endpoint with
   > the narrow field mask `references.externalIds`, 500 arXiv IDs per request,
   > ~6,200 requests total, paced at 1 request/second. Results are cached to local
   > disk so no repeat requests are made.

3. 提交。官方说几个工作日；实际经常当天或次日就到。

### 3.2 拿到 key 之后放哪里

**不要把 key 贴进聊天、不要提交进 git。** 建一个文件：

```powershell
# 在仓库根（与 lunyun 同级）
cd D:\Develop\研云\研云\交付到4090
Set-Content -Path lunyun\.env.local -Value "S2_API_KEY=你的key" -Encoding utf8
```

抓取脚本读 `process.env.S2_API_KEY`（或 `lunyun/.env.local`）。
接线时会把 `.env.local` 加进 `.gitignore` 并**验证它确实被忽略**（`git check-ignore -v`），
不靠"我记得加了"。

### 3.3 key 的限额（这决定要跑多久）

| 项目 | 值 |
|---|---|
| 限额 | **1 请求/秒**，**所有端点共用**这一个额度 |
| 建议节奏 | 1.25 秒/请求（留余量，别贴着上限） |
| 单次批量上限 | `/paper/batch` 一次最多 **500 个 id** |
| 单次响应上限 | **10 MB**（所以要窄字段，别把 `citations`/`references` 的嵌套字段全要上） |
| 遇 429 | 读 `Retry-After` 头，按它等，别立刻重试 |

## 4 拿到 key 之后怎么做（已经算好，照着跑）

### 4.1 主方案：batch 抓引用列表

```
POST https://api.semanticscholar.org/graph/v1/paper/batch
     ?fields=references.externalIds
header: x-api-key: <key>
body:   { "ids": ["ARXIV:2401.00010", "ARXIV:1706.03762", ...] }   // 最多 500 个
```

| 项 | 估算 |
|---|---|
| 论文总数 | 3,052,327 |
| 每批 | 500 篇 → **6,105 次请求** |
| 节奏 | 1.25 s/请求 → **约 2.1 小时** |
| 响应体积 | 约 1 MB/次 → 合计约 **6 GB**（流式解析，不落盘） |
| 产出 | `data/cites-edges/<d>.bin`：每条边 `u32 本文 docId \| u32 被引 docId`，只保留**两端都在我们库里**的边 |

> 6,105 这个请求数和当年抓引用计数的次数**完全一样**，那一次是跑通的 ——
> 所以这个量级是被验证过的，不是估算。

**只保留两端都在库里的边**：我们的库是纯 arXiv，一条边只要有一端对不上，
就没有坐标可画；留下来只会变成"点了没反应"的悬空数据。

### 4.2 先跑一个小样本验通路（**别一上来就跑全量**）

```powershell
# 抽 5,000 篇（10 次请求，约 13 秒），只验证：能通、字段对、映射率是多少
node lunyun\pipeline\harvest-references.mjs --sample 5000
```

这一步要看两个数：
* **命中率**：`references.externalIds.ArXiv` 里有多少能对上我们的 `docId`；
* **每篇平均引用数**：决定最终边数（若平均 20 条、命中率 30%，则约 1,800 万条边）。

样本数对不上预期就先别跑全量 —— 先查字段名，不要用 2 小时换一个"字段写错了"。

### 4.3 备选：Datasets API 一次下整份

拿到 key 之后值得先试这一条（可能比 6,105 次请求快得多）：

```
GET https://api.semanticscholar.org/datasets/v1/release/latest
GET https://api.semanticscholar.org/datasets/v1/release/latest/dataset/references
```

第三个端点会返回**下载链接**（parquet，含 `corpusid → cited corpusid`）。
我们要的是"corpusid ↔ arXiv 号"的对照（`/paper/batch` 里带 `externalIds` 就能建），
然后就能把整份引用边直接过滤成我们的 docId 对。

**这条路没有实测过**（没有 key 访问不了），所以它是"值得先试"，不是"一定行"。

### 4.4 建图之后的验收（必须做，不然等于没做）

1. **边数对得上**：抽样 200 条边，逐条回查两端论文，确认"引用方向"没反
   （被引方的年份应当 ≥ 引用方，或者同年的会议/期刊版本差异要能解释）。
2. **反向自检**：我们已有的 `cites` 计数（被引次数）与图中"入度"应当**同量级**；
   若差一个数量级，说明映射错了一半。
3. **可画率**：统计有多少条边的两端都能算出坐标（应当在 100%，因为建图时就过滤过）。

## 5 拿不到 key 怎么办（降级方案）

不阻塞其他工作。丝线层是**数据源无关**的，可以先用手上真实存在的关系画：

| 方案 | 数据源 | 代价 | 表达的语义 |
|---|---|---|---|
| **同路线丝线**（推荐降级） | `semantic/<d>.route.bin` 里两端都在演示点集里的边，离线筛成 `public/data/edges/<d>.bin` | 约 1.4 万条边 / **168 KB** | 「同一技术路线」—— 由标题+摘要嵌入算出，**不是引用** |
| 跨学科丝线 | 元数据索引里的 `FLAG_CROSS_LISTED` | 每团要载 `meta/<d>.idx.bin`（物理团 **89 MB**） | 「这篇挂了别的学科分类」 |

**界面上必须写清楚是哪一种**，不能把"语义近邻"标成"引用" —— 这个作品的核心
卖点就是"位置与关系都由数据算出、不编造"，标注错了比不画更糟。
