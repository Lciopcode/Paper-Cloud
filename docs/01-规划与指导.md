# 论文云 · 规划与指导

> 本文是实施蓝图：技术路线、四阶段计划、验收标准、GPU 迁移方案、风险与应对。
> 配套阅读：`00-总结.md`（现状）、`03-架构设计.md`（模块边界）、`02-参赛方向与规划.md`（备赛打法）。

## 一、总体技术路线

### 1.1 一句话路线

```
arXiv 元数据（已有）
      ↓
① 离线数据管线（Node）        → 语料、引用、领域层级、影响力评级
② 离线语义管线（Python+GPU）  → embedding、聚类、社区发现、技术路线标签
③ 静态资产构建（Node）        → 编号脊柱、层级坐标、关系图、分片二进制
      ↓
④ 纯静态前端（React + three） → 八层宇宙、三类关系边、三种排列模式
```

**关键约束**：②是唯一需要 GPU 的环节，**它离线产出静态文件，前端不依赖 GPU 算力**。
理由：① 评委不会给你 4090；② 这也是"高内聚低耦合"的体现——GPU 侧是独立管线，前端只读产物。

### 1.2 为什么 GPU 只用于离线

| 环节 | 能否放前端 | 原因 |
|---|---|---|
| embedding 计算 | ❌ | 305 万篇 × 1024 维，浏览器算不完 |
| 聚类 / 社区发现 | ❌ | 同上 |
| 层级坐标求解 | ❌ | 图布局是全局计算 |
| 渲染 / 拾取 / 检索 | ✅ | 已有 LOD + 流式加载 + 顶点着色器过滤 |
| 相似论文推荐 | ✅ | 读预生成的 k-NN 列表 |

## 二、四阶段实施计划

### P0 · 基座换域（本机可完成，先做）

**目标**：在 v2 上把"诗"换成"论文"，引擎跑通，能显示八层结构的第一屏。

| 子任务 | 产出 | 验收 |
|---|---|---|
| P0-1 语料导出 | `text/<domain>.jsonl.gz`（8 个，约 2 GB） | 每行 `{id, title, abstract, authors, cats, year}`，可搬迁 |
| P0-2 词表与编号脊柱 | 每学科 `vocab.json` + `spine.bin` | `unrank(rank(title)) === title` 对抽样 10 万条成立 |
| P0-3 双射散射 | `scatter.ts`（对合+仿射构造） | 单测：双射性、无不动点塌缩、雪崩性 |
| P0-4 地址表 | `cell.bin` + 二分 | "这个地址上真有论文吗"判定 100% 正确（抽样验证） |
| P0-5 层级数据结构 | `Hierarchy` 类型 + 读取 | 能按 8 层下潜，层级计数自洽（子级之和 = 父级） |
| P0-6 第一屏渲染 | 8 个学科超星系团 | 首屏加载 < 2 MB，8 个团可见、可点、可聚焦 |

**本机就能做完 P0 的全部内容**（Node + 已有 305 万篇语料），不需要 GPU。

### P1 · GPU 语义层（需 4090 机器）

**目标**：算出"具体研究点（星云）"与"技术路线（恒星）"。

| 子任务 | 方法 | 产出 |
|---|---|---|
| P1-1 环境准备 | Python 3.11/3.12 + CUDA torch + faiss-gpu + sklearn | 可跑的环境 |
| P1-2 embedding | `BAAI/bge-m3`，标题+摘要，256 token 截断 | 305 万 × 1024 维 → Matryoshka 截断 256 维 + int8 ≈ **0.8 GB** |
| P1-3 多分辨率聚类 | GPU k-means，k ∈ {200, 1000, 5000} | topic 标签（每篇 2–3 字节） |
| P1-4 簇内 k-NN | FAISS-GPU，k=16（**只在簇内建边**，否则 9600 万边吃不消） | 近邻列表 |
| P1-5 社区发现 | Louvain/Leiden（CPU 多核，分簇并行） | **技术路线（恒星）划分** |
| P1-6 路线命名 | 与 OpenAlex `primary_topic`/`keywords` 交叉验证，贴可读标签 | 路线名（"扩散模型加速采样"而不是"路线 #4711"） |

**算力预算**（4090，实测口径）：

| 任务 | 耗时 |
|---|---|
| embedding 标题+摘要（305 万篇 ≈ 7.7 亿 token） | **1.5–3 小时** |
| embedding 仅标题（验证版，≈ 4600 万 token） | **~10 分钟** |
| k-means 多分辨率（5–10 档 × 300 万 × 256 维） | 每档 5–8 分钟 |
| FAISS-GPU k-NN（k=16） | **~15 分钟** |
| Louvain/Leiden | 1–2 小时 |

### P2 · 层级与关系图（本机可完成主体，需 P1 产物）

| 子任务 | 说明 | 验收 |
|---|---|---|
| P2-1 领域层级抓取 | OpenAlex 按 DOI 批量（**200 条/次**），取 `domain/field/subfield/topic/keywords` | 覆盖率 ≥ 90%（抽样） |
| P2-2 引用边抓取 | S2 `/references`（**高影响子集优先，20–30 万篇**） | 骨架图 ≤ 3 GB（brotli 后 ~0.6 GB） |
| P2-3 三类边构建 | 引用（有向）+ 同领域 + 同路线（共被引 ∩ 语义近邻） | 每条边可溯源到数据，不靠猜 |
| P2-4 八层坐标求解 | 层级嵌套半径 ∝ √count；路线恒星位置由社区中心定；论文轨道半径由影响力/时间定 | 位置确定性：同一输入永远同一坐标 |
| P2-5 Obsidian 式浏览 | backlinks / outgoing / unlinked mentions / local graph / 边过滤器 | 选中论文能看到三类邻居并高亮 |
| P2-6 反向索引 | 正向边建 CSR 反向索引 | 查"被谁引用" O(1) |

### P3 · 视觉、模式与参赛材料（本机可完成）

| 子任务 | 说明 |
|---|---|
| P3-1 八层视觉落地 | 宇宙网 → 超星系团 → 星系群 → 星系 → 星团 → 星云 → 恒星 → 行星 |
| P3-2 三种排列模式 | 时间顺序 / 影响力 / 综合，**界面上由用户选择**（见 §四 双坐标设计） |
| P3-3 四种交叉可视化 | 星尘流、拉格朗日点、跨星系星桥、超新星遗迹（引力透镜最后评估） |
| P3-4 影响力编码 | 引用次数→亮度、发表评级→大小 |
| P3-5 性能与降级 | LOD、视锥裁剪、渐进流式；低画质档自动关闭后处理 |
| P3-6 参赛材料 | 演示视频、作品说明书、资源授权清单、AI 使用披露表、自检报告 |

## 三、开发顺序（本机优先，GPU 后置）

按你的要求"**先在本机完成基本编码与设计工作，有大概样子再上 4090**"：

```
第 1 步（本机）  P0 全部  →  能看到八层结构第一屏、能点开论文、关系丝线可见
第 2 步（本机）  P2-1/P2-4/P2-5 的「不依赖语义层」部分
                 →  用 OpenAlex 层级先把八层坐标跑通（哪怕星云/恒星是空的）
第 3 步（GPU）   P1 全部  →  产出 embedding + 聚类 + 社区 → 拷回本机
第 4 步（本机）  P2-2/P2-3 + P3  →  关系边、三种模式、四种交叉可视化
第 5 步（本机）  参赛材料
```

**为什么这样排**：八层坐标的**骨架**可以先只用 OpenAlex 层级搭起来（第 2 步），
这样即使 GPU 那边还没跑，你也能先看到"大概的样子"并调整视觉；
等 GPU 产物回来，只是把"星云/恒星"这两层填上，不用返工。

## 四、坐标稳定性设计（关键决策）

三种排列模式会重排位置。若不做处理，用户会"记不住东西在哪"，永久链接也会失效。

**方案：双坐标**

| 坐标 | 定义 | 用途 |
|---|---|---|
| **规范位置**（canonical） | 层级 + 引用拓扑决定，**永不变** | 永久链接指向它；跨会话稳定；默认视图 |
| **模式视图**（mode view） | 在规范位置上按权重做一次布局变换 | 切模式时平滑过渡动画，切回即复原 |

| 模式 | 轨道半径 | 大小 | 颜色 |
|---|---|---|---|
| 时间顺序 | 年份（越早越靠内） | 引用量 | 固定或按路线区分 |
| 影响力 | 影响力得分（越高越靠内） | 引用量 | 年份（暖=老，冷=新） |
| 综合 | 多维加权 $r = w_1\hat{y}+w_2\hat{c}+w_3\hat{s}+w_4\hat{x}$ | 引用量 | 年份或学科 |

模式选择写入 URL（`&m=impact`），**规范位置始终可还原**。

## 五、GPU 迁移方案

### 5.1 需要带走什么

| 内容 | 体积 | 说明 |
|---|---|---|
| `text/*.jsonl.gz` | ~2 GB | 语料（GPU 管线的输入） |
| `requirements-gpu.txt` | 极小 | 依赖清单 |
| `pipeline_gpu/*.py` | 极小 | 脚本（含断点续跑） |
| `scripts/setup-gpu.ps1` / `.sh` | 极小 | 一键环境安装 |

**只搬 2 GB**，不搬 10.7 GB 的 SQLite。

### 5.2 环境准备清单（GPU 机器）

1. **Python 3.11 或 3.12**（当前 3.14 太新，torch 无稳定轮子；两版可并存）
2. **CUDA 版 PyTorch**（对应显卡驱动）
3. `sentence-transformers` / `transformers`
4. **`faiss-gpu`**（GPU k-NN）
5. `scikit-learn`（k-means 基线）
6. `python-louvain` / `igraph`（社区发现）
7. `pyarrow` / `duckdb`（读写 parquet，接 OpenAlex 快照与中间产物）

### 5.3 断点续跑（必须做）

GPU 机器可能被打断（跑 3 小时的任务不能白跑）：

- embedding **分片落盘**（每 10 万篇一个 `.npy`），已有分片自动跳过
- 聚类、k-NN、社区发现各自独立成步，产物带版本号与输入哈希
- 每步有 `--force` 与 `--resume` 两个开关

### 5.4 拷回来的产物

| 产物 | 体积 |
|---|---|
| `emb/<domain>.i8.npy`（256 维 int8） | ~0.8 GB |
| `cluster/<domain>.bin`（topic/route 标签） | ~20 MB |
| `routes.json`（路线清单一：id、标签、质心、规模、代表论文） | ~5 MB |

## 六、验收标准（每阶段）

### P0 验收
- [ ] 引擎单测全绿（双射性、往返、地址表判定）
- [ ] 首屏加载 ≤ 2 MB，8 个学科超星系团可见
- [ ] 点开任意一篇论文能看到元数据与编号
- [x] 编号 ⇄ 标题双射由 `src/engine/spine.assets.test.ts` 用真实资产验证（原「虚空拉取」已于 2026-10 删除）

### P1 验收
- [ ] 抽样 20 个"星云"，人工检查是否确实是同一研究点（**这一条必须人工看，不能只看指标**）
- [ ] 每条"技术路线"能贴出一个可读标签，且与 OpenAlex topic 不矛盾
- [ ] 交叉论文（多归属）抽检合理

### P2 验收
- [ ] 八层下潜可走通：宇宙 → … → 单篇论文
- [ ] 三类边各自可开关，边数在预算内
- [ ] 选中论文能看到 backlinks / outgoing / unlinked mentions
- [ ] 层级计数自洽（子级之和 = 父级）

### P3 验收
- [ ] 三种模式切换有平滑过渡，切回默认复原
- [ ] 四种交叉可视化各自可用（引力透镜可不做）
- [ ] 弱机降级可用（低画质档不崩）
- [x] ~~过曝像素率 < 1.5%~~，色相分布不过度集中
      ⚠️ **这条已作废（见 `02-参赛方向与规划.md` 第 75 行）**：1.5% 这个数是在**离屏读回**里量的，
      而那个离屏 RenderTarget 当时漏了 sRGB 编码（默认线性、画布是 sRGB），读数系统性偏暗约 2.5×，
      于是"守住 1.5%"的几档实际上是把画面压暗换来的 —— 参考实现的观感恰恰来自大面积过曝。
      现改为 **离屏口径 过曝 < 5%**（`deploy/verify.mjs` 的闸门），实测 **2.223%**；
      **整页口径**（含 bloom 与 HUD）实测 **2.09%**（诗云参照帧 0.468%）。
      **教训**：指标本身没错，错在量它的那台尺子是坏的；先修尺子，再谈守不守线。
      ⚠️ 更进一步的教训（2026-10）：**尺子修好之后还会再错一次** ——
      `side-by-side.mjs` 用 max 通道、各 `probe-*.mjs` 用 luma，同一帧差 10 以上。
      现已合并成 `_scratch/metric.mjs`，**指标只定义一次**。
      ⚠️ 第三次教训（2026-10，最贵的一次）：**尺子对了，被测对象也可能是错的**。
      第 14 轮那张选档扫描表全部是在"自动降级之后手动切回 high"的状态下量的，
      而那时 **bloom 并没有随画质切回来**（见 `Galaxy.tsx` 里那一大段的实测）——
      于是整张表量的是"没有辉光"的画面。**"探针跑通了"不等于"量的是你想要的那个东西"。**

## 七、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| **S2 限速** | 引用图覆盖不全 | 高影响子集优先 + 按需拉取；已获用户认可 |
| **OpenAlex 批量上限** | 层级抓取慢 | 按 DOI 200 条/批；分片断点续跑；抽样验证覆盖率 |
| **GPU 机器环境难装** | P1 阻塞 | 提供一键脚本 + requirements 锁定版本 + 失败回退 CPU（慢但可行） |
| **聚类质量不可控** | "星云"看着不像研究方向 | 与 OpenAlex topic 交叉验证；提供人工标签兜底；UI 不宣称官方分类 |
| **300 万点性能** | 浏览器卡死 | LOD + 视锥裁剪 + 上限 30 万点 + 低画质档 |
| **版权与字体** | 参赛资格风险 | 资源授权清单；**绝不打包楷体等系统字体**；只展示元数据不分发 PDF |
| **模仿指控** | 创新性扣分 | 署名写全 + 答辩主动说明 + 创新点落在诗云没有的三处（八层/三类边/影响力编码）<br>⚠️ **2026-10 落实**：此前"署名"只写在文档里、README 完全没提、`LICENSE` 文件根本不存在，而文档却声称"LIMIT 已写明不含其代码"——**这是比抄袭更危险的状态：说了假话**。现已补 `LICENSE`（第三方组件一节含 Required Notice + 逐文件清单）与 README 致谢，并删除全部"不含其代码"表述 |
| **引力透镜成本高** | 拖累进度 | 放最后，可能不做 |

## 八、开发规范要点（详见 CONTRIBUTING.md）

1. **高内聚低耦合**：模块边界见 `03-架构设计.md`，跨层只走契约，不跨层直接读文件
2. **分阶段提交**：每个可验收的子任务一次提交，提交信息写清"做了什么 + 怎么验的"
3. **契约先行**：数据结构改动必须先改契约文件与文档，再改实现
4. **自检随行**：新功能必须带单测或自检脚本，否则不提交
