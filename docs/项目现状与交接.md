```bash
cd lunyun                      # ← 本项目就是 lunyun/ 一个目录（原文写的 v2/lunyun 是 v1 时代的路径）
```

产出：embedding → **按层自适应**聚类（第 5 层「研究点」）→ 层内 k-NN → 社区发现（第 6 层
「技术路线」+ 同路线边）→ c-TF-IDF 给研究点起名

> ⚠️ 原文这里写的是"**多分辨率**聚类"，那是 v1 的设计（k ∈ {200,1000,5000}）。
> 实际实现是**按层自适应**：每层的簇数 = `clip(round(sqrt(m/2)), 2, 64)`（m 是该层篇数），
> 所以簇数是随数据规模变的，不是固定的几档。详见 `pipeline_gpu/README.md`。
解锁：**同路线边**、**拉格朗日点可视化**、**语义近邻**（Obsidian 式浏览的 unlinked mentions）

### P3 —— 需要申请 API key 才能做

**引用边（backlinks + 反向索引）** 两条路都堵着：
- S2 `/references` **不能批量**（一篇一次请求），20–30 万篇 = 80+ 小时
- OpenAlex `referenced_works` 可以批量，但要先建「OpenAlex ID → docId」映射表 = 30,524 次请求 = 30 天配额

**解法**：申请一个 [Semantic Scholar 学术 API key](https://www.semanticscholar.org/product/api#api-key-form)（免费）。
有了 key 之后 `/references` 的限速从共享池变成 1 请求/秒的专属额度，20 万篇约 55 小时可跑完，
而且可以并发。

### P4 —— 锦上添花

- 八层视觉的中间层（星系群 / 星团 / 星云）目前只在层级面板里以数据呈现，
  可以做成真正的三级缩放下潜
- 引力透镜可视化（视觉风险最高，最后评估）

## 四、换机器：git 与数据怎么对接

### 4.0 现状：**这是一个纯本地仓库，没有远端**

```bash
$ git remote -v
（空）
$ git branch --show-current
master
$ git rev-list --count HEAD
34
```

所以"对接"有两条路，按你的网络条件选。

> ⚠️ **关键认知：仓库里只有代码和文档（3.1 MB），没有数据。**
> 数据分三处，都**不在仓库里**（`.gitignore` 都排除了）：
>
> | 目录 | 大小 | 内容 | 能不能重建 |
> |---|---|---|---|
> | `public/data/` | 4.4 GB（跑完语义层约 5.5 GB） | 构建产物（脊柱/元数据/检索/关系/引用）+ 语义层成品 | ✅ 能，但要先有语料 |
> | `text/` | 1.3 GB | 导出的 JSONL.GZ（GPU 语义层的输入） | ✅ 能，来自语料 |
> | **`corpus/`**（**与仓库同级**，即 `<交付根>/corpus/`） | 5.4 GB | arXiv 原始语料 SQLite（每学科一个 `domain_<id>.db`） | ❌ **不能**，是抓下来的原始数据 |
>
> **结论：`corpus/` 是唯一不可再生的东西（5.4 GB），必须单独拷。**
>
> ⚠️ 原文写的是 `data/corpus/`（**在 v1 目录下**）—— 那是开发机布局。
> 本交付里它在**仓库的上一级**，而且脚本会依次试 4 个候选路径来自动找到它
> （见 `pipeline/export-text.mjs` 的 `resolveCorpus()`；本包命中第 2 个候选
> `<仓库>/../corpus`，已实测）。想放到别处就传 `--corpus <路径>`。

### 4.1 数据永远不进 git —— 但有一处例外

`data/cites/*.bin`（**11 MB，已入库**）—— 这是**故意的**：

- 引用数据抓取很慢（受 API 配额限制），重建成本高
- 11 MB 对仓库可接受
- 一并入库的还有 `.part*.bin` 分片与 `.progress.json` ——
  于是**抓取的续跑状态也随仓库走**，在新机器上 `pnpm harvest:cites` 能从断点继续

抓取器的单实例锁 `data/cites/.harvest.lock` **不入库**（运行时产物）。

> `data\raw\`、`citations\` 等）。本交付里 `lunyun\` **直接在交付根目录下、没有 `v2\` 这一层**，
> 上面已按实测值重写；`data\corpus\`、`data\raw\`、`citations\` 在本包里都**不存在**
> （语料在交付根的 `corpus\`，见 §四）。

| 删什么 | 省多少 | 代价 |
|---|---:|---|

| `shots\*.png` | 16 MB | 无（纯留证） |
| `node_modules\` | 191 MB | `corepack pnpm install` 重建；本来就不打包 |

## 六、环境依赖与已知的坑

### 6.1 依赖

| 需要 | 版本 | 说明 |
|---|---|---|
| Node.js | **≥ 22**（用到 `node:sqlite`） | 本机用的是 DSH 附带的 v24.21.0 |
| pnpm | 任意近期版本 | — |
| 浏览器 | Chrome / Edge（支持 WebGL2） | 演示用 |
| Python（仅 GPU 语义层） | 3.11/3.12 + CUDA | 见 `pipeline_gpu/setup-4090.md` |

**不需要**：任何后端服务、数据库、网络（上面命令全部本地）。

### 6.2 已知的坑

| 坑 | 说明 |
|---|---|
| **资产不可压缩的例外** | `public/data/meta/*.{idx,txt,abs,venue}.bin` 与 `public/data/search/*.idx.bin` **必须保持未压缩** —— 浏览器用 HTTP Range 精确取字节。压缩后无法随机访问，且报错很难懂 |
| **`dist/` 不再含数据** | `vite.config.ts` 里设了 `copyPublicDir: false`。原来每次构建都产生 4.3 GB 的 `dist/data` 副本，而服务器根本不从那里取数据（它直接映射 `public/data`）。关掉后构建从 12–20s 降到 **7s**，磁盘少占 4.3 GB |
| **OpenAlex 日配额是 1000 次** | 不是官方文档说的 10 万次。**读响应头** `x-ratelimit-limit` 才知道。全量引用抓取靠它跑不通（要 30 天） |
| **抓取器只能跑一个实例** | 已加单实例锁（`data/cites/.harvest.lock`）。两个进程共享进度与分片文件会**损坏数据** —— 实测差点发生 |
| **服务器不需要重启** | `deploy/serve.mjs` 每次请求都从磁盘读 `dist`。改代码后 `pnpm build` + **刷新页面**即可 |
| **无头环境的帧率不能代表真机** | 自检用 SwiftShader 软件渲染，只有 2–3 fps。判据只看**相对关系**，不看绝对 fps |
| **`shots/` 会长得很快** | 每次无头自检产生一个约 256 MB 的 Chrome profile。跑一批自检后记得清理（`shots\_*`） |

### 6.3 演示机建议

本机是 **AMD 核显**，无头自检靠软件渲染。真机演示：
- **有独显的机器体验会明显更好**（146 万点是一次 draw call，独显毫无压力）
- 即使没有独显，自动降级会兜底并如实告知
- 4K 屏上也没问题（点精灵在顶点着色器里算尺寸）

## 七、决策记录（为什么这么做）

这一节记录**为什么放弃了某些看起来更"完整"的做法**。评委常问这类问题。

### 7.1 为什么没有"八层"的完整视觉层级

规划里写的是宇宙网 → 超星系团 → 星系群 → 星系 → 星团 → 星云 → 恒星 → 行星。
实际落地为：**8 个学科星系（L1）→ 一级学科（L2）→ 研究方向（L3）+ 下潜**。

原因：**层号在构建期就写进了每篇论文的编号**，所以"看某一层"是一次 O(1) 判断，
不需要新数据也不需要重新索引。把中间层做成真正的三级缩放动画是**表现层**工作，
而先把"层级真的能被查询"这件事做扎实更有价值 —— 后者才是这个作品的立身之本。

### 7.2 为什么影响模式缺数据时**明确留空**而不是凑合

`cites` 在语料里全库为 0。在引用数据到位之前，`impactPosition()` 是**直接抛错**的，
而不是用"发表去处等级"冒充影响力 —— 那会给出一个**看起来合理、实际错误**的图景，
比"功能不可用"更糟。现在引用数据到了，影响模式才被实现。

### 7.3 为什么严格区分「0 引用」与「没有记录」

两者数值都是 0，但意义完全不同：

- **查到 0 引用** —— 这篇确实还没被引用过，该画得很暗；
- **没有记录** —— 我们**不知道**它被引用了多少次，不该假装它很暗。

混在一起会让"不够知名的论文"和"数据缺失的论文"看起来一样，
而这恰恰是做「引用 → 亮度」最容易误导人的地方。
所以 `CiteTable` 暴露 `hasRecord`，界面显示覆盖率，
影响模式里**"无记录"单独落最外一环**。

### 7.4 为什么低画质档压的是点尺寸而不是减少点数

实测：`uScale` 1.0 → 0.8 让帧率变化 **1.00 倍**（等于没降级）。
瓶颈是**填充率**（每个点精灵最大 30px，146 万个点铺满屏幕时像素着色器是瓶颈），
不是顶点数（顶点着色器里那点 `sin` 开销可以忽略）。
所以改成 `uScale` 1 → 0.5、像素上限 30px → 14px。

### 7.5 为什么不把"减少动态效果"只写在 CSS 里

星点闪烁是在**顶点着色器**里做的（6 万个点各自呼吸），CSS 管不到。
只写 `@media (prefers-reduced-motion)` 会得到一个"看起来做了无障碍"的假象。
正确做法是把这条偏好一路传到着色器，`uTwinkle` **直接归零**
（不是调小 —— 这条偏好的语义是"别动"）。
