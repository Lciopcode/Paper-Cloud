# 提交规范（分阶段提交）

> 目的：**方便追查与回溯**。每个提交必须是一个"可验收的最小单元"，而不是"今天干了啥"。

---

## 一、提交单位：一个可验收的子任务

对照 `docs/01-规划与指导.md` 的阶段编号来切：

| 提交前缀 | 含义 | 例子 |
|---|---|---|
| `p0:` | 阶段 P0（基座换域） | `p0(engine): 编号脊柱 + 双射散射，17 单测` |
| `p1:` | 阶段 P1（GPU 语义层） | `p1(embed): bge-m3 分片落盘与断点续跑` |
| `p2:` | 阶段 P2（层级与关系图） | `p2(rel): 三类边构建 + CSR 反向索引` |
| `p3:` | 阶段 P3（视觉与模式） | `p3(view): 三种排列模式与双坐标过渡` |
| `docs:` | 纯文档 | `docs: 参赛方向候选池与倒向条件` |
| `chore:` | 工程配置、依赖、脚本 | `chore: 继承 v1 构建配置` |
| `fix:` | 修 bug（**必须写清复现方式**） | `fix(engine): Feistel 逆轮序写错导致散射不可逆` |
| `feat:` | **新增能力**（不属于某个阶段编号时） | `feat(semantic): 前端接上第 6 层技术路线` |
| `perf:` | **纯性能/内存优化，输出不变** | `perf(embed): 改成单遍流式，不再重复解压` |
| `test:` | **只加/改测试**，不动实现 | `test(semantic): 契约测试遍历 manifest 每个学科` |

> **后三种是接手后补进这张表的**（原表只有前七种）。原因很实在：
> 上一轮的工作大量落在"**修既有阶段的实现缺陷**"与"**补规格里没写但必须有的东西**"上，
> 用 `p1:`/`p2:` 反而不如 `fix:`/`feat:` 准确 —— 阶段前缀回答的是"哪个阶段"，
> 而这几类提交回答的是"**这次改动的性质**"。
> 两种维度都有用，所以并存；选哪个按"能不能一眼看出改了什么性质"来定。
>
> ⚠️ 用 `perf:` 时有一条**硬要求**：必须证明**输出没变**。
> 本项目采用的做法是对同一输入跑改前/改后、比对产物哈希
> （例：`community.py` 向量化那次，`route.bin` 的 SHA256 逐字节相同）。
> 只说"应该没变"不算。

**不许**出现的提交：
- `update`、`修改`、`今天的工作` —— 无法追查
- 一次提交混多个阶段（例如同时改引擎和视觉）
- 提交里带未通过单测的代码

## 二、提交信息格式

```
<前缀>(<范围>): <做了什么>

为什么：<动机 / 解决什么问题>
怎么验：<可复现的验证方式，命令或步骤>
边界：<已知限制 / 没做的事>
```

**真实例子**（本仓库第 1 个业务提交）：

```
p0(engine): 编号脊柱与双射散射

为什么：目录不被存储、被计算 —— 标题要能双向映射到几十位编号，
        且相邻编号在空间上不能相邻（否则星海排成整齐螺旋，没有宇宙感）。
怎么验：pnpm test → src/engine/spine.test.ts 17 项全绿，含
        · 小目录（7^5）穷举验证 rank/unrank 双射且满射
        · 散射在全目录上穷举，输出无重复、无遗漏
        · 47 位十进制真实规模下散射可逆、不溢出
边界：散射采用 width-2h 的 Feistel + 固定宽度 cycle-walk；
      与诗云的半宽 cycle-walk 实现不同（后者在 R 不是置换并集时不是双射）。
```

## 三、提交前必须过的三道门

```bash
# ⚠️ 本机 pnpm 不在 PATH 上，用 corepack 前缀（见 README 的说明）
corepack pnpm typecheck   # 类型必须干净
corepack pnpm test        # 单测必须全绿（当前 180 项 + 1 项可跳过）
corepack pnpm lint        # 内嵌资源扫描
# 改了可视化或交互时，还要跑浏览器自检（17 项，约 496 秒，会自己起服务器）：
corepack pnpm verify:all
```

> 原文写的是"P3 阶段会补 `verify:e2e`" —— **它早就补上了**，
> 而且 `package.json` 里现在有一整套：`verify:all / e2e / mobile / layout / keys /
> css / cites / perf / permalink / a11y / drill`。
> 建议直接用 `verify:all`（它把 17 项串起来跑，并自动清理无头浏览器的 profile 残骸）。

**新功能没有测试就不许提交** —— 这类"数学不变量"一旦悄悄坏掉，
表现是"看起来正常但结果错"，比崩溃更难查。

## 四、架构纪律（高内聚低耦合的具体含义）

| 层 | 目录 | 允许依赖 | 禁止 |
|---|---|---|---|
| **引擎层** | `src/engine/` | 只能依赖自身 | 不许 import 数据加载、three、React、DOM、fs |
| **数据层** | `src/data/` | 引擎层 | 不许 import three / React |
| **渲染层** | `src/three/` | 引擎层、数据层、three | 不许直接读文件（必须走数据层） |
| **界面层** | `src/ui/` | 状态层、数据层 | 不许直接碰 three 对象 |
| **状态层** | `src/state/` | 引擎层、数据层 | 不许 import three / React 组件 |
| **离线管线** | `pipeline/` | 引擎层（**同一份实现**） | 不许复制引擎逻辑；必须 import 同一文件 |
| **GPU 管线** | `pipeline_gpu/` | 无（独立 Python） | 只读 `text/*.jsonl.gz`，只写 `emb/`、`cluster/` |

**为什么管线必须 import 同一份引擎**：如果离线算编号用一套代码、浏览器算编号用另一套，
两边一旦有差异，用户点开论文就会"编号对不上"——这种 bug 极难发现。
所以引擎层是**唯一的真相来源**，管线与前端都必须用它。

**契约先行**：任何数据结构改动，先改 `src/data/contract.ts` 与对应文档，再改实现。

## 五、分支策略

单人开发为主，保持简单：

| 分支 | 用途 |
|---|---|
| `main` | 始终可运行、单测全绿 |
| `feat/<阶段>-<主题>` | 大改动（超过 1 天的），做完合并回 main |

**不合并就不提交到 main。** 每个阶段完成时打一个 tag：`p0-done`、`p1-done`…

## 六、什么不进 git

见 `.gitignore`。原则：

| 类型 | 是否入库 | 理由 |
|---|---|---|
| 源码、文档、配置、测试 | ✅ | 核心资产 |
| `data/corpus/`、`public/data/` | ❌ | 数 GB，可由管线重建 |
| **引用/语义抓取结果**（`data/citations/`、`emb/`） | ✅（若有大小限制则例外） | **受第三方限速，重跑代价高，属于不可再生资产** |
| `node_modules/`、`dist/` | ❌ | 可重装/重建 |
| 字体文件（`.ttf/.woff`） | ❌ **绝不入库** | 字体授权风险，参赛前置审查项 |
